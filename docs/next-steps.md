## Возможное развитие, не блокирующее текущий учебный план

- Настоящий источник оперативных заказов и свободных курьеров. Пока его нет, основной экран остаётся честным демонстрационным сценарием.
- Настоящее время переезда и маршруты после выбора подходящего источника.
- Настройка гиперпараметров с ограниченным бюджетом как ещё один дополнительный компонент.
- Развёртывание с HTTPS для доступа с других устройств вне этого компьютера. Сейчас Compose публикует веб-порт только на 127.0.0.1.

## Задание следующему исполнителю

Начать с пункта 1 после команды пользователя продолжать реализацию. До изменения кода прочитать `AGENTS.md`, `requirements.md`, `monitoring-decisions.md`, `data-and-features.md`, затем текущий код загрузки признаков и мониторинга. На момент составления этого плана пользователь просит таблицу для просмотра, а не запуск всех следующих работ.

Для дрейфа сначала определить и записать признаки, опорный и текущий периоды, метод сравнения и минимальный объём данных. Опорная выборка должна быть зафиксирована; её нельзя каждый раз заменять текущей, иначе изменение станет незаметным. Не использовать незавершённые сутки или будущие значения. Отдельно учитывать пропуски и различия зон/календаря. Нехватку данных показывать явно. Дрейф означает изменение входных данных и сам по себе не доказывает рост ошибки модели.

Сохранить результат на сервере с версией правила и границами выборок, добавить простое объяснение в интерфейс. Проверить неизменённые данные, выраженный сдвиг, недостаточную выборку, пропуски, повторный запуск и сохранность исходных прогнозов. Учебные сдвиги проверять в изолированных данных, не подменяя рабочие наблюдения.

Перед пунктами 2–6 отдельно зафиксировать устройство хранения обученной модели и признаков, ссылку на активную версию, правила конкурентных запусков и протокол оценки. Кандидат не должен проверяться на днях, вошедших в его обучение. Сравнение активной и новой модели должно использовать одинаковые доступные условия; если это требует временного переобучения обеих моделей или накопления новых контрольных прогнозов, выбрать подход явно и описать его. Существующий итоговый тест из отчёта нельзя незаметно превратить в набор для многократного подбора.

Каждый этап доводить до работающего интерфейса/API, необходимых тестов, проверки в Docker и обновлённой документации. Не заменять проект другим шаблоном и не вводить большую внешнюю платформу ради реестра без конкретной необходимости. Возможности PostgreSQL и существующего MinIO следует оценить первыми; модельные артефакты хранить отдельно от аватаров.
