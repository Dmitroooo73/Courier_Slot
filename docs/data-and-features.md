# Данные и признаки

## Два источника

1. Синтетический текстовый журнал сервиса заказов: `data/raw/order_events/ГГГГ-ММ-ДД.log`. Строки содержат время, уровень, вид события, необязательные поля и свободный текст. Встречаются служебные записи и повторная доставка событий. Парсер извлекает ID, время и зону заказа; результат нормализуется в суточный CSV. Это слабоструктурированный источник, прямо предусмотренный методичкой как журнал событий.
2. Публичный HTTP JSON Open-Meteo: вложенные почасовые массивы времени, температуры и осадков. Сохраняется исходный ответ, затем значения агрегируются по московским суткам. Для обучения используется архив прогнозов с заблаговременностью 48 часов, а не погода, измеренная после прогнозируемого дня.

CSV — производная таблица заказов, а не третий независимый источник. Старый кэш CSV остаётся совместимым; новые отсутствующие дни проходят через журнал событий. Заказы синтетические, персональных данных в обучающих наборах нет. Учётные записи приложения хранятся отдельно и не участвуют в моделировании.

Генератор фиксирует seed=42, различия между зонами и недельную сезонность. Погода не участвует в генерации заказов. По этим данным нельзя делать выводы о реальной причинной связи погоды и доставки.

## Нормализация событий

Пример входа:

```text
2026-11-11T09:10:00+03:00 INFO order.created zone=east order_id=demo-1 channel=demo | Order accepted
2026-11-11T09:10:00+03:00 INFO order.created order_id=demo-1 zone=east | Retry
2026-11-11T09:11:00+03:00 DEBUG service heartbeat
2026-11-11T23:59:59+03:00 INFO export.complete
```

Порядок полей не фиксирован. Одинаковое повторное событие считается один раз. Два разных события с одним ID — ошибка, требующая исправления источника. Служебные строки не считаются заказами. В этом фрагменте только одна зона, поэтому он иллюстрирует формат; для полной выгрузки нужны все шесть зон.

Импорт внешнего журнала того же контракта:

```powershell
python -m backend.pipeline.import_events events.log --date 2026-11-11 --data-dir data
```

Команда не заменяет уже существующий CSV другим содержимым. Нормализация завершается до атомарной записи. Для учебного источника отсутствие заказов в зоне трактуется как неполная выгрузка: настоящие нулевые сутки потребуют отдельного сигнала полноты по каждой зоне.

## Контроль качества

| Проверка | Решение |
| --- | --- |
| Пустой ID, неизвестная зона, неправильное время, заказ за пределами суток | Прервать загрузку, записать причину; последний успешный прогноз остаётся доступен |
| Повтор события с теми же ID, временем и зоной | Не считать второй раз |
| Конфликт полей одного ID, дубликат ID в нормализованном CSV | Прервать загрузку |
| Нет завершающей записи журнала или данных по одной из зон | Не публиковать неполный день |
| Разная длина погодных массивов, неверные единицы, нечисловые значения, отрицательные осадки | Отклонить ответ источника |
| Не хватает почасовых значений погоды | Суточный признак остаётся пропуском, а не нулём |
| Необычное число заказов | Отметить в сводке качества, сохранить исходное значение |

Для необычного спроса сравниваем день с последними восемью такими же днями недели в этой зоне. Нужно хотя бы четыре прошлых наблюдения. Условие: `|заказы − медиана| > max(6 × MAD, 0,5 × медиана, 1)`, где MAD — медиана абсолютных отклонений от медианы. Порог использует только прошлое. Скачок может быть настоящим спросом, поэтому автоматически удалять его нельзя. Сохраняются число сигналов и до десяти примеров. Это проверка отдельных наблюдений; полноценный дрейф распределений пока не реализован.

В проверке на 11 ноября 2026 года: 365 дней, 250 829 заказов, 0 сигналов необычного спроса и 29 неполных дней погоды в загруженном погодном диапазоне. Нулевое число сигналов означает только прохождение указанного правила.

## Признаки и время

Прогноз на день D выпускается накануне в 20:00 мск. Полностью закрытый последний день — D−2. Одна функция `features_for_day` строит признаки для обучения, валидации и прогноза:

| Группа | Признаки | Обработка |
| --- | --- | --- |
| История заказов | D−2, D−7, D−14; среднее D−8…D−2 | Только завершённые сутки |
| Календарь | День недели | Категория, не порядковая числовая величина |
| География | Одна из шести условных зон | Категория |
| Погода | Средняя температура, сумма осадков, число часов с осадками | Суточная агрегация; пропуски сохраняются |

Ridge: one-hot для категорий, медиана только обучающего окна для пропусков, индикаторы пропуска и стандартизация чисел. CatBoost получает категории отдельно и обрабатывает пропуски числовых признаков при построении деревьев. Во всех случаях обучение преобразований выполняется внутри соответствующего временного окна.

## Отбор и проверка полезности

Рабочий выбор сравнивает базу и две модели в вариантах с погодой/без погоды. Победитель определяется по MAE трёх временных окон до отдельного теста. Это фактический отбор погодной группы.

Отдельная диагностическая проверка Ridge исключает погоду, историю заказов и день недели по очереди. Все варианты используют те же 504 наблюдения валидации; отложенный тест не используется для выбора групп. Результат хранится в `model-results.json`.

| Вариант Ridge | MAE, заказа | Изменение против всех признаков |
| --- | ---: | ---: |
| Все признаки | 5,5655 | 0 |
| Без погоды | 5,5675 | +0,0020 |
| Без истории заказов | 5,5536 | −0,0119 |
| Без дня недели | 6,3532 | +0,7877 |

На этом синтетическом наборе надёжно видна польза календаря. Польза погоды практически отсутствует; лаги избыточны относительно зоны и календаря. Разницу в сотые и тысячные заказа не считаем доказанным улучшением. Диагностический эксперимент не заменяет опубликованную модель автоматически: её набор признаков и исходные прогнозы остаются воспроизводимыми. Упрощённый кандидат можно проверить при внедрении реестра моделей.

Тесты проверяют исключение D и D−1 из признаков, сохранность результата при изменении будущих заказов, обработку пропусков, одинаковые результаты повторного импорта и сохранение прошлого прогноза при ошибке источника.
