# Обновление модели: рабочая версия, проверка новой, замена и откат

Короткий ответ. Ежедневный прогноз считает одна сохранённая **рабочая версия** модели, без нового обучения. Если мониторинг две недели подряд видит слишком большой промах, планировщик обучает **новую версию** и сравнивает обе на одних и тех же днях, которых не было в их обучении. Новая версия заменяет рабочую только при выигрыше не меньше 5%. Администратор может одной кнопкой вернуть предыдущую версию. Опубликованные прогнозы, факты и решения мониторинга при этом не меняются.

Где смотреть: «Качество → Обновление модели» — текущая версия, последняя проверка и журнал. «Мониторинг → Замена модели» — полный цикл на учебных данных.

## Правила

Каждое правило имеет версию. При изменении алгоритма вводится новая версия, сохранённые записи не переписываются.

| Правило | Что делает |
| --- | --- |
| `retrain-v1` — повод | Планировщик ставит задание, если у зоны сохранено решение мониторинга `alert` (две полные недели выше порога `weekly-error-v1`). Все 14 дней этого решения должна прогнозировать текущая рабочая версия; сигнал о прежней версии задание не создаёт. Повторный сигнал в течение 7 дней после задания по той же версии новое задание не создаёт; задание, прерванное сбоем, паузу не включает. Администратор может запустить проверку вручную. |
| `candidate-v1` — новая версия | Тот же код признаков и та же процедура выбора (база, Ridge, CatBoost, с погодой и без, три окна валидации и отдельный тест). Обучение — только на днях до контрольной недели с отсечкой 20:00. Свежие дни весят больше: вес дня уменьшается вдвое каждые 14 дней (`recency_half_life_days` в паспорте). |
| Контрольная неделя | 7 последних закрытых дней по всем шести зонам. Обе версии обучены не позже чем за два дня до её начала, поэтому эти дни не участвовали в обучении ни одной из них. Если рабочая версия обучена позже, честного окна нет — проверка ждёт (интерфейс показывает дату). |
| `promotion-v1` — замена | Новая версия становится рабочей, если на контрольной неделе её средний промах (MAE) не больше 95% промаха рабочей версии и не больше промаха прогноза «как неделю назад». Иначе она сохраняется в реестре со статусом «проверялась» и причиной отказа. В работу выходит ровно тот экземпляр, который проверяли. |
| Откат | Администратор возвращает версию, работавшую до текущей. Рекомендуемый повод — рост промаха в мониторинге после замены. Действие проверяет, что рабочая версия не сменилась с момента открытия страницы. Прогноз, уже опубликованный на завтра, не заменяется: откат действует со следующего вечернего расчёта. |

Почему вес свежих дней. На учебных данных первой версии со сдвигом спроса +35% в одной зоне обычное переобучение на годе истории почти не помогло (MAE 10,4 против 11,1): модель опирается на средний уровень зоны за год. С полураспадом 14 дней промах снизился до 6,6. Без сдвига тот же приём даёт выигрыш около 1%, и правило 5% честно отклоняет такую версию. Эксперимент повторяет `backend/tests/test_lifecycle.py` и учебный цикл.

**Новая версия данных.** Если рабочая модель обучена на другой версии данных (поле `orders_source` в паспорте), worker при запуске один раз обучает новую рабочую версию стандартной процедурой. Запись в журнале — «Новая версия данных» (`data_version`). Вернуть модель, обученную на другой версии данных, нельзя: кнопка отката её не предлагает, API отвечает 409.

## Ежедневный прогноз

Worker читает рабочую версию из `active_forecast_model`, загружает артефакт из реестра, проверяет контрольную сумму, версию признаков и окружение. Затем строит признаки на дату общим кодом `features_for_day` и публикует прогноз с `forecast_mode = saved_model`. Метрики в «Качестве» относятся к проверке этой версии; если она пришла на замену, сверху показано, почему: «на контрольной неделе … промах X против Y».

На чистом стенде рабочей версии нет. Первый вечерний расчёт один раз обучает её стандартной процедурой (шаг журнала «Обучение первой модели»), дальше только прогнозирует. Существующий стенд можно перевести на сохранённую версию командой, которая сверяет паспорт с архивным прогнозом той же даты:

```powershell
docker compose exec worker python -m backend.modeling.initialize_active --version <ID из реестра>
```

## Хранение

| Таблица PostgreSQL | Содержимое |
| --- | --- |
| `active_forecast_model` | Одна строка: рабочая версия и контекст прогноза (центр объяснений Ridge, диапазоны сценариев, исходная проверка). Меняется только через активацию. |
| `model_activations` | Журнал: первая версия, замена, откат; кто, когда, почему, предыдущая версия и полный контекст. Запись не изменяется. |
| `model_candidates` | Задания проверки: повод, статус (`queued`, `training`, `activated`, `rejected`, `failed`), контрольная неделя, MAE/WAPE всех трёх вариантов по зонам и по дням, решение с проверками. Уникальный ключ повода не даёт создать дубль; частичный уникальный индекс допускает только одно открытое задание. |
| `model_versions` | Паспорт и артефакт каждой версии, включая отклонённые. |
| `lifecycle_demos` | Итог учебного цикла. Отдельный ключ; рабочие таблицы он не трогает. |

Замена выполняется одной транзакцией: новая версия, журнал, задание и указатель рабочей версии. Обновление указателя идёт с условием «рабочая версия всё ещё та, что ожидалась». В файловом режиме те же записи лежат в `data/active_forecast_model.json`, `data/model_activations/`, `data/model_candidates/`.

Обучение идёт только в worker под общей блокировкой ежедневных операций. Веб-процесс ставит задание, worker замечает его в течение минуты. Если проверка прервалась (например, нет сети), задание получает статус `failed`; при следующем сигнале или запросе с тем же поводом оно возвращается в очередь, счётчик попыток растёт.

## API

- `GET /api/models` — реестр; на первой странице поле `lifecycle`: правила, рабочая версия с датой, последние задания, журнал, версия для отката и готовность ручной проверки.
- `POST /api/admin/models/candidates` — только администратор: поставить проверку на последних 7 закрытых днях. Ответ 202 — задание создано, 200 — возвращено существующее, 409 — нет честного окна или рабочей версии.
- `POST /api/admin/models/rollback` с `{"expected_version_id": "..."}` — только администратор. 409, если версия уже сменилась, предыдущей нет или идёт расчёт.
- `GET /api/lifecycle-demo` — итог учебного цикла.

## Учебный цикл

`backend/modeling/demo_cycle.py` проигрывает 13 октября — 12 ноября 2026 года тем же кодом, что и в работе, со сдвинутыми часами. Это вечерний прогноз в 20:05, сверка после полуночи, решения мониторинга, правило переобучения, проверка и откат. Всё происходит во временном каталоге: исходные CSV копируются, на Востоке с 20 октября добавляется 35% явно помеченных заказов (`…-east-shift-N`). Сохраняется только итог.

Что показывает проигрыш на версии данных `synthetic-weather-v2`:

1. 19 октября администратор запускает проверку без повода — новая версия на 19,3% хуже, отказ.
2. 20 октября спрос на Востоке растёт; 21 октября — предупреждение.
3. 28 октября — две недели выше порога, задание по сигналу. Контрольная неделя 22–28 октября, новая версия ещё не видела сдвиг и хуже на 2,2% — отказ.
4. 4 ноября повторный сигнал (недельная пауза прошла). Контрольная неделя 29 октября — 4 ноября: MAE 6,69 против 10,05, на Востоке 12,3 против 30,7. Новая версия точнее на 33,4% и переходит в работу. Прогноз на 5 ноября уже опубликован прежней версией, новая прогнозирует с 6 ноября.
5. Промах на Востоке после сдвига: 32,3 заказа в день до замены и 8,4 после. 12 ноября последняя неделя снова в пределах порога.
6. 13 ноября откат. Проверено, что опубликованные прогнозы сохранили свою версию, а повторный сигнал второго задания не создал.

На первой версии данных (`lifecycle-demo-v1`, сохранён в базе) картина та же по смыслу: отказ без повода, ложная тревога в зоне без сдвига (выигрыш 4,8% < 5%), замена с промахом на Востоке 37,6 → 9,8.

Worker строит итог один раз после запуска (около 30 секунд), если его ещё нет. Пересчитать вручную:

```powershell
docker compose exec worker python -m backend.modeling.demo_cycle --force
```

## Проверки

- `test_lifecycle`: граница правила 5% и сравнение с базой; граница чистого окна; сигнал о прежней версии не создаёт задание; одно задание на повод и одно открытое задание; недельная пауза; полный цикл на синтетике со сдвигом (обучение первой версии, кандидат, замена, конфликт отката по устаревшей версии, откат и журнал).
- `test_http_integration`: права администратора и заголовок браузера; 409 без честного окна; 202 и затем 200 на повторный запрос; конфликт отката по устаревшей версии; откат и журнал без контекста в ответе.
- `test_daily`: чистый стенд обучает первую версию один раз; сбой этого шага пишет журнал и сохраняет прежний прогноз; планировщик вызывает шаг обновления модели.

Ограничения. Проверка опирается на 42 наблюдения (7 дней × 6 зон), поэтому выигрыш около порога 5% чувствителен к шуму. Порог выбран для учебной системы и не калиброван по частоте ложных замен. Автоматического отката нет: решение о возврате принимает администратор.
