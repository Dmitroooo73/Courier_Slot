# Пульт доставки

Учебный веб-пульт по дисциплине «Проектный практикум». Тема № 15 — «Доставка готовой еды». Главный экран помогает разобраться с решением курьера «остаться или сменить район» на явно вымышленном примере. Отдельные вкладки показывают суточный прогноз по шести условным зонам Москвы, объяснения, качество и мониторинг. Заказы синтетические; оперативного источника пока нет.

Репозиторий: [Dmitroooo73/Courier_Slot](https://github.com/Dmitroooo73/Courier_Slot).

## Быстрый запуск приложения

С установленным и запущенным Docker Desktop:

~~~powershell
git clone https://github.com/Dmitroooo73/Courier_Slot.git
cd Courier_Slot
docker compose up -d --build
~~~

Открыть [пульт на этом компьютере](http://127.0.0.1:8765). Первый запуск показывает базовое демо, пока worker загружает погоду и рассчитывает полное сравнение. Ход расчёта: `docker compose logs -f worker`. Для MinIO используется закреплённый образ; если он недоступен в реестре, ниже описан перенос через `docker save/load`. Доступность скачивания этого образа на другом компьютере пока не подтверждена.

[Требования и проверки](docs/requirements.md) · [Данные и признаки](docs/data-and-features.md) · [Технический отчёт](docs/report.md) · [Результаты моделей](docs/model-results.json).

[Сценарий курьера и ограничения](docs/courier-scenario.md). При открытии приложения выводится вкладка «Курьер». Без свежих заказов, числа курьеров и маршрута она не рекомендует переезд. В учебном примере можно переключить короткую дорогу, долгую дорогу и устаревшие данные. Суточный прогноз раскрывается ниже; аналитические вкладки сохранены.

## Запустить первый прогноз

Из корня проекта, на Python 3.11 или новее. Устанавливать пакеты не нужно.

~~~powershell
python -X utf8 -m backend.pipeline
~~~

Чтобы вывести только Восток, запустите `python -X utf8 -m backend.pipeline --zone east`. Флаг фильтрует таблицу в терминале. В JSON по-прежнему сохраняются все шесть зон.

Демо считает прогноз на 24 октября 2026 года для шести условных зон Москвы. Команда генерирует CSV за 14 завершённых суток, обрабатывает сохранённый архивный выпуск погоды и печатает прогноз и превышение мощности по зонам. Базовая модель берёт число заказов семь дней назад. Погодные показатели выводятся рядом с прогнозом, чтобы проверить импорт. Они понадобятся моделям на следующем этапе.

- `data/raw/orders/` содержит посуточные CSV синтетических заказов.
- `data/raw/weather/` содержит исходный ответ API.
- `data/processed/` содержит таблицу с одной строкой на сутки и зону.
- `data/forecasts/2026-10-24.json` содержит итог по зонам, погодные показатели и сведения об источниках.
- `data/runs/` содержит журнал. В нём видны новые и повторно использованные сутки, источник погодного выпуска и этап ошибки.

Для подготовки года истории заказов запустите `python -X utf8 -m backend.pipeline --history-days 365`. Повторный запуск генерирует только отсутствующие посуточные CSV. Результат публикуется после проверки обоих источников. Если загрузка или проверка не проходит, прежний прогноз остаётся доступен, а команда завершает работу с ошибкой.

Флаг `--fetch-weather` заново запрашивает выпуск через интернет. Временные ошибки и лимиты API приводят к повтору запроса с паузой. Флаг `--date ГГГГ-ММ-ДД` меняет дату прогноза, для новой даты понадобится доступ к архиву. Флаг `--data-dir ПУТЬ` задаёт каталог результатов. Каждый прогон загружает погоду для одной целевой даты.

Проверки запускаются командой `python -X utf8 -m unittest discover -s backend/tests -v`.

В проект включён ответ Open-Meteo для модели ECMWF IFS HRES, выпуск от 23 октября 2026 года в 00:00 UTC. Данные предоставлены Open-Meteo на условиях CC BY 4.0. [Источник и условия использования](https://open-meteo.com/en/docs/single-runs-api)

## Сравнить модели

Один раз создайте окружение в папке проекта и установите библиотеки.

~~~powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-ml.txt
~~~

Запустите сравнение и покажите прогноз для Востока.

~~~powershell
.\.venv\Scripts\python.exe -X utf8 -m backend.modeling --zone east
~~~

Команда использует год учебных заказов. Она сравнивает сезонную базу, Ridge и CatBoost на трёх последовательных окнах по 28 дней. Для обеих обучаемых моделей проверяются варианты с погодой и без неё. Победитель по MAE сравнивается с базой на отдельных последних 28 днях. Затем выбранная модель обучается на всей истории, доступной к отсечке, и выдаёт прогноз по зонам. В `data/evaluations/2026-10-24.json` сохраняются метрики, факты и прогнозы на тестовом окне, параметры, версии библиотек и контрольная сумма набора данных.

Для моделей используем отдельный погодный ряд с заблаговременностью 48 часов. Он доступен к отсечке накануне в 20:00, в том числе для последних часов прогнозных суток. Первый прогон запрашивает архив через интернет, последующие догружают только отсутствующие даты. Неполные сутки отмечаются как пропуск. Ridge заполняет пропуски медианой обучающего окна, CatBoost обрабатывает их при обучении деревьев. Заказы в текущей симуляции генерируются независимо от погоды, поэтому сравнение демонстрирует отбор признаков на учебных данных. [Open-Meteo Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api)

## Открыть веб-пульт

Из корня проекта запустите Docker Compose.

~~~powershell
docker compose up -d --build
~~~

Откройте [веб-пульт](http://127.0.0.1:8765). Compose запускает PostgreSQL, импортирует сохранённые отчёты и журнал из `data/`, затем поднимает пульт и ежедневный планировщик на 20:00 мск. На чистом запуске создаётся базовый демопрогноз. Повторный импорт пропускает уже существующие записи.

PostgreSQL хранит опубликованные прогнозы, метрики, объяснения и журнал запусков в именованном томе `postgres_data`. Кэш исходных заказов и погоды лежит в `data/`. Посмотреть состояние можно командой `docker compose ps`, а журнал планировщика — `docker compose logs worker`. Команда `docker compose down` останавливает пульт с сохранением данных в томе. Если порт 8765 занят, перед запуском задайте `$env:PULT_PORT = "8768"` и откройте [порт 8768](http://127.0.0.1:8768).

### Локальный запуск через Python и Node.js

Для первой сборки понадобятся Python 3.11+ и Node.js 22.12+ или 20.19+. Если окружение `.venv` уже есть, начните с установки веб-зависимостей.

~~~powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-web.txt
npm --prefix frontend ci
npm --prefix frontend run build
~~~

Если папка `data/` пустая, выполните базовый прогон или сравнение моделей по инструкции выше. Затем из корня проекта запустите сервер.

~~~powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8765
~~~

Откройте [веб-пульт](http://127.0.0.1:8765) или [документацию API](http://127.0.0.1:8765/docs). В меню доступны вкладки «Прогноз», «Качество», «Мониторинг» и «Журнал». Восток выбран при открытии. Клик по карте переключает карточку, а ссылка в карточке открывает график той же зоны на вкладке «Качество». Красным выделяются зоны, где число заказов выше плановой мощности. Выбор «Последний прогноз» автоматически подхватывает самую свежую сохранённую дату.

Кнопка «Почему такой прогноз?» в карточке зоны показывает вклад каждого признака в заказах. Для Ridge это отклонение от среднего прогноза на обучающей истории, рассчитанное по коэффициентам модели. Для CatBoost используется SHAP. Сезонная база показывает дату и число заказов неделей ранее. Для старого отчёта модели без объяснений запустите `backend.daily --date ГГГГ-ММ-ДД --force` через Python из `.venv`.

Во вкладке «Качество» рейтинг признаков можно посмотреть за все три окна валидации или за отдельный период. Средний модуль вклада измеряет сдвиг прогноза, а перемешивание значений показывает, насколько меняется MAE.

Внизу вкладки «Качество» блок «Что изменится, если…» показывает реакцию выбранной модели на изменение одного условия. Выберите зону, температуру или число заказов неделю назад, затем передвиньте ползунок. Карточка сравнит исходный прогноз с результатом сценария в заказах. Диапазон берётся из истории выбранной зоны. Модель рассчитывает каждую точку с теми же остальными признаками. Это индивидуальная кривая зависимости прогноза от признака. [Описание метода ICE](https://scikit-learn.org/stable/modules/partial_dependence.html#individual-conditional-expectation-ice-plot)

Для существующих отчётов сценарии можно добавить командой `docker compose exec worker python -m backend.modeling.backfill_scenarios`. Она восстанавливает модель при совпадении версии данных, библиотек, параметров и исходных прогнозов. Новые ежедневные отчёты включают сценарии сразу.

В режиме «По заказам» планировщик фиксирует первый прогноз, выпущенный до начала целевых суток, и после их закрытия подсчитывает учебные заказы. Он сверяет пропущенные дни при запуске. Порог недели равен средней опорной ошибке опубликованных моделей за эту неделю плюс 30%. После одной полной недели выше порога пульт показывает предупреждение, после двух подряд рекомендует переобучение.

В «Учебном сценарии» выберите зону, вариант «Заказов больше» и нажмите «Запустить проверку». Пример показывает 14 прошлых дней с увеличенным числом заказов. После первой полной недели система может показать предупреждение, после двух подряд — рекомендацию обновить модель. Кнопка «Обычный спрос» позволяет проверить те же дни с исходным числом заказов. Обычный промах берётся из валидации по зоне или из 14 дней перед сценарием для старых отчётов.

В режиме «По заказам» вывод рассчитывает и сохраняет сервер. Под графиком находится история «Что решила система»: нажмите на дату, чтобы увидеть причину и недельные пороги. Она хранится в PostgreSQL, переживает перезапуск и одинакова на устройствах, подключённых к этому пульту. Повторы не создают дублей; после сбоя недостающие решения восстанавливаются. Учебный сценарий эту историю не меняет. [Правило, устройство хранения и проверки](docs/monitoring-decisions.md).

В режиме «По заказам» до закрытия дня показываются сохранённый прогноз и дата ожидаемой сверки. Например, прогноз на 11 ноября сверяется после 00:00 мск 12 ноября. Журнал раскрывается нажатием на запись и позволяет открыть связанный прогноз. История хранится в PostgreSQL и общая для устройств, подключённых к одному серверу. В текущем Compose порт опубликован на `127.0.0.1`, поэтому доступен на этом компьютере.

FastAPI читает отчёты из PostgreSQL при заданном `PULT_DATABASE_URL`. При локальном запуске без этой переменной он читает JSON из `data/` или каталога из `PULT_DATA_DIR`. React опрашивает API раз в минуту и по кнопке «Обновить». Когда доступны оба отчёта за дату, веб-пульт показывает результат сравнения моделей, а при наличии только базового расчёта показывает его.

## Аккаунты и админка

После `docker compose up -d --build` откройте [«Аккаунт»](http://127.0.0.1:8765/#account) и зарегистрируйтесь. Для прогноза вход не нужен. Список аккаунтов доступен администраторам. Чтобы выдать эту роль зарегистрированному аккаунту, выполните из папки проекта команду с его логином.

~~~powershell
docker compose exec web python -m backend.admin МОЙ_ЛОГИН
~~~

Обновите страницу после назначения роли. В «Админке» доступны сводка по аккаунтам и сессиям, поиск по логину или имени, фильтры и карточка пользователя. Администратор может завершать сессии обычного пользователя и управлять доступом к входу.

В «Аккаунте» сначала открывается карточка профиля. Кнопка «Редактировать» показывает разделы с личными данными, аватаром и паролем. Профиль доступен владельцу и администраторам. Для демонстрации используйте вымышленные данные. Смена пароля требует текущий пароль и завершает все сессии аккаунта.

Аватары хранятся в MinIO в томе `avatar_data`. Docker использует закреплённый образ из RPG. Если его нет на другом компьютере, перенесите образ через `docker save` и `docker load` или укажите доступный образ MinIO через `PULT_MINIO_IMAGE`. Для доступа к внешнему MinIO задайте `PULT_MINIO_ENDPOINT`, `MINIO_ROOT_USER` и `MINIO_ROOT_PASSWORD` в окружении процесса FastAPI. Для HTTPS к хранилищу задайте `PULT_MINIO_SECURE=1`.

Короткий токен хранится в памяти вкладки и действует до 15 минут. Длинный токен хранится в `HttpOnly` cookie, меняется при каждом обновлении и восстанавливает вход после перезагрузки страницы до истечения семидневной сессии. Выход завершает текущую сессию сразу. Пароли хранятся в PostgreSQL в виде хешей Argon2id. При запуске за HTTPS установите `PULT_AUTH_SECURE_COOKIE=1`, чтобы cookie отправлялась только по HTTPS.

При запуске Python без Docker для аккаунтов установите `requirements-db.txt`, задайте `PULT_DATABASE_URL` и один раз выполните `python -m backend.bootstrap` из окружения проекта с зависимостями ML. Прогнозы из локальных JSON доступны и без подключения базы.

## Ежедневный прогноз

Разовый запуск из корня проекта с установленными зависимостями из `requirements-ml.txt`.

~~~powershell
.\.venv\Scripts\python.exe -X utf8 -m backend.daily
~~~

Одна команда догружает заказы и погоду, обучает модели и сохраняет отчёт, который читает веб-пульт. До 20:00 мск команда готовит пропущенный прогноз на сегодня, с 20:00 — прогноз на завтра. Для уже опубликованной даты расчёт пропускается. `--date ГГГГ-ММ-ДД` выбирает доступную дату, `--force` заменяет сохранённый результат после успешного расчёта. Журнал пишется в `data/runs/`.

Для запуска по расписанию откройте отдельное окно PowerShell в папке проекта.

~~~powershell
.\.venv\Scripts\python.exe -X utf8 -m backend.daily --watch
~~~

Пока процесс открыт, в 20:00 мск он запускает расчёт на следующие сутки. При старте он проверяет самый свежий положенный прогноз, поэтому может догнать пропуск. Если прогон завершился с ошибкой, планировщик повторит попытку через пять минут, а пульт продолжит показывать последний сохранённый результат. Остановка — `Ctrl+C`. `PULT_DATA_DIR` позволяет использовать с пультом общий нестандартный каталог.

## Что строим

Веб-пульт для диспетчера службы доставки. Каждый вечер в 20:00 по местному времени система выпускает прогноз на следующие календарные сутки для каждой зоны. Диспетчер видит, где ожидается много заказов и где прогноз выше плановой мощности зоны. Мощность задаётся в заказах в сутки.

Для первой версии берём один город и шесть условных зон. Считаем уникальные заказы по дате оформления в местном часовом поясе. На главном экране — зоны, отсортированные по превышению мощности, фильтры по зоне и дате, график факта и прогноза, ошибка моделей и время последнего обновления.

## Данные

| Источник | Что забираем | Как обновляем |
| --- | --- | --- |
| Синтетический текстовый журнал заказов → CSV | Из событий извлекаются ID, время оформления и зона; служебные строки исключаются, одинаковые повторные события не удваивают заказы. История на 12 месяцев с недельной сезонностью | Генератор с seed=42 публикует журналы по завершённым суткам. Парсер проверяет полноту и создаёт суточные CSV; старый кэш CSV сохраняется |
| Open-Meteo, HTTP JSON | Почасовые массивы температуры и осадков. Из них считаем суточную температуру, сумму осадков и число часов с осадками | Сохраняем исходный ответ, время получения, модель погоды и выпуск прогноза. Для обучения берём архив выпусков, доступных к моменту прогноза спроса. [API прогноза](https://open-meteo.com/en/docs), [архив выпусков](https://open-meteo.com/en/docs/single-runs-api) |

На панели явно маркируем заказы как синтетические. Они позволяют проверить систему и сценарии защиты. Влияние погоды на реальный спрос можно оценить только по реальным данным. Если моделируем погодный эффект в генераторе, задаём его отдельно от погодного прогноза, который получает модель спроса.

Сохраняем исходные файлы и JSON, нормализованные записи, витрину признаков, прогнозы и метрики. Загрузчик ведёт журнал запусков и догружает пропущенные даты. Повторная загрузка тех же данных даёт тот же результат без дублей. Ошибки API, таймауты и лимиты видны в журнале. При сбое сохраняем последний успешный результат и отмечаем его дату. Проверяем уникальность заказов, полноту суток по зонам и целостность почасовых массивов. Неполный день помечаем как пропуск.

## Как прогнозируем

- Один расчёт признаков для обучения и прогноза. Для даты `D` используем только информацию, доступную накануне в 20:00. Признаки включают спрос за `D−2`, `D−7` и `D−14`, среднее за последние семь завершённых дней, день недели и погоду из уже доступного выпуска. Для линейной модели зону и день недели кодируем one-hot, поскольку у категорий нет естественного порядка.
- Сравниваем три модели на одинаковых датах и зонах. База — число заказов семь дней назад. Две другие — Ridge и CatBoost. Отдельно сравниваем модели с погодой и без неё, чтобы оценить вклад источника.
- Делим данные по датам. На ранних периодах обучаемся, на следующих окнах проверяем, самый свежий период держим для финальной оценки. Обработку пропусков и отбор признаков настраиваем внутри обучающих окон. Фиксируем seed, версию данных и параметры запуска. Тест на утечку меняет будущие заказы и проверяет, что более ранние признаки и прогнозы совпали.
- Показываем MAE в заказах на зону в сутки и WAPE в процентах, когда сумма фактических заказов больше нуля. Выбираем модель по временной валидации. Если базовый прогноз точнее, он остаётся рабочим.

## Как устроен пульт

~~~mermaid
flowchart LR
    Orders["Текстовые события заказов → CSV"] --> Worker["worker · проверка данных и расчёт"]
    Weather["Open-Meteo · прогнозы погоды"] --> Worker
    Worker -->|"Кэш входных данных"| Files["Каталог data/"]
    Files -->|"Кэш для повторного прогона"| Worker
    Files -->|"Сохранённые отчёты"| Init["init · схема базы и импорт"]
    Init --> DB[("PostgreSQL 17")]
    Worker -->|"Прогноз, качество и сверка"| DB
    Web["web · FastAPI"] <-->|"Отчёты, аккаунты и сессии"| DB
    Web <-->|"Аватары"| Media["MinIO"]
    UI["Браузер · React"] <-->|"HTTP API"| Web
~~~

Docker Compose сначала запускает `db`, затем `init` создаёт таблицы и импортирует сохранённые результаты. После этого `worker` считает прогноз на завтра в 20:00 мск и сверяет заказы после полуночи. `web` читает опубликованные результаты из PostgreSQL, поэтому браузер получает их сразу. Интерфейс запрашивает сводку через `GET /api/dashboard`, а аккаунты и админка используют `/api/auth` и `/api/admin`.

Из RPG-проекта взяли идею отдельных роутов и сервисов FastAPI, компонентный интерфейс и схему с двумя токенами. В пульте расчёты находятся в `backend/modeling/`, загрузка и запись результатов — в `backend/pipeline/`, а страницы и типизированные запросы — в `frontend/src/`.

Дополнительные компоненты выбираются самостоятельно. У интерпретируемости реализованы четыре пункта из методички. Мониторинг пока включает проверку ошибки и рекомендацию переобучения, а управление версиями моделей остаётся следующим этапом.

## Что показать на защите

1. **Карта перегруза.** Закрашиваем зоны по превышению мощности. Например, при прогнозе 142 и мощности 120 зона показывает «+22 заказа сверх плана». Клик открывает историю и прогноз зоны. Числа здесь иллюстративные.
2. **«Почему такой прогноз?»** Для выбранной зоны и даты показываем объяснение той версии, которая выпустила прогноз. Для CatBoost выводим вклады SHAP в заказах, для Ridge — вклады линейных членов, для базовой модели — число заказов в тот же день прошлой недели. Глобальную важность сравниваем по средним абсолютным вкладам и перестановке признаков на временных окнах. Ползунок в блоке «Что изменится, если…» показывает зависимость прогноза от одного признака.
3. **Симуляция смены спроса.** Проигрываем отдельный период со скачком заказов в одной зоне. Панель показывает изменение среднего спроса и рост ошибки по мере проигрывания дней. После двух недель подряд с превышением порога система показывает рекомендацию переобучить модель. Реестр версий, сравнение перед активацией и откат остаются в плане.

В методичке дополнительные компоненты стоят до 30 баллов суммарно. Приоритет — объяснения и мониторинг. Если останется время, третий компонент — подбор гиперпараметров с фиксированным бюджетом и воспроизведение запуска по ID из журнала.

В методичке указано согласование темы в первые три недели и запрет повторов в группе. Материалы загружаются в ЛМС к сроку, который объявляет преподаватель. Статус согласования и дату сдачи нужно уточнить перед календарной разбивкой этапов.
